## How the build is structured (why the real error is invisible)
The CodeBuild BUILD phase runs TWO things concurrently:
1. `eval "docker buildx build --builder emergent-builder --platform linux/arm64 --provenance=mode=min --push -f Dockerfile.cloudbuild --target final-build ... ." &` → **backgrounded**, `BUILD_PID`.
2. (CF_ENABLED) `docker run ... build-frontend-artifacts.sh` → builds the React app and syncs it to R2 **in the foreground**.

The script ends with `wait $BUILD_PID`. The foreground R2 job prints hundreds of `cp … s3://…` lines and finishes with `[FRONTEND_BUILD] Build completed successfully!`. The backgrounded buildx failed **earlier**, so its stderr is interleaved far above the tail and is flooded out by the R2 upload output.

**Log-retrieval limitation (answering "get the window after the first 500 lines"):** `get_build_logs` (filtered and raw) returns only a single ~500-line **tail** window for this build and exposes **no offset/pagination**. I grepped that window for every buildx signature — `failed to solve`, `exit code`, `[backend-build]`, `[frontend-build]`, `package_local_engine`, `backend`, `137`, `Killed`, `pushing`, `writing image` — **all absent**. The window contains only: the R2-upload tail, the CodeBuild shell echo (lines 471–481), and POST_BUILD/UPLOAD_ARTIFACTS (482–500). **The actual buildx RUN + stderr + exit code is not obtainable with the available tooling.** It exists in the raw CloudWatch log stream for this build id and must be read there by infra.

## What I PROVED (sandbox on this run's pulled source, /app/scratch)
1. **Requirements snapshot NOT updated.** `grep -cvE '^\s*(#|$)' backend/requirements.txt` = **147**, not the intended 46. The frontend optimization IS present (no `*.map` in `frontend/build`), but the backend requirements trim was **not** in the source this build pulled. (Real source/sync gap — see Fixes.)
2. **compileall cannot fail the build.** All three invocations in `Dockerfile.cloudbuild` (lines 282, 296, 301) end in `|| echo "[BUILD_LOG] WARNING…"`, so any non-zero exit (incl. a killed child) is swallowed → RUN exits 0. The "compileall returns 1" hypothesis is ruled out by the manifest itself.
3. **pip install is clean on arm64 — no source builds.** `pip download --no-deps --only-binary=:all:` for aarch64/cp311/abi3/none across all 145 pins (litellm + emergentintegrations are installed separately by the Dockerfile and `sed`-removed) → **every package has a binary wheel**. aarch64-specific wheels require at most `manylinux_2_28` (base image glibc is newer), so `pip install --no-dependencies` compiles nothing. litellm (hardcoded whl) and emergentintegrations==0.2.2 (emergent index) both resolve.
4. **Frontend builds fine.** The parallel `build-frontend-artifacts.sh` R2 job completes successfully on every run; `scripts/package_local_engine.py` exits 0 (restores the committed offline browser-wheel archive + checksum-verifies 15 runtime assets). No source maps.
5. **All COPY sources exist:** `pip-cache/pip-wheels`, `pip-cache/pip-bin`, `frontend/`, `backend/`, `entrypoint.sh`, `nginx.conf`.

Net: **no application-source or manifest-driven `RUN` command can account for the failure** — each is independently proven to pass on arm64, or is guarded.

## Root cause (confirmed platform blocker)
The backgrounded `docker buildx build` (arm64, `--push` to ECR, builder `emergent-builder`) exits 1 with diagnostics that the deploy pipeline does not surface — it only reports the generic `exit status 1` from `wait $BUILD_PID`, and the image is never pushed. Because every source/manifest RUN is proven green and no buildx stderr is retrievable, the fault is in the **build-execution/plumbing layer**, not the app code: the arm64 BuildKit build itself, the `--push` to ECR, or the build host — to be confirmed from the raw BuildKit stderr.

The pipeline also has an **observability defect**: backgrounding buildx and surfacing only `wait`'s exit code means the real error is routinely flooded by the parallel CF R2-upload output. This is why the failure has been un-diagnosable across runs.
