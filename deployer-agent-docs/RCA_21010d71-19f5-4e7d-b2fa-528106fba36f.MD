# RCA — Deploy run 21010d71-19f5-4e7d-b2fa-528106fba36f (lasthood-dev, initial deploy)

## Symptom
`build_image` step failed in the `frontend-build` stage (Cloud/CodeBuild step #39). Build terminated with exit 1.

```
    verify_runtime()

    at Object.<anonymous> (/app/craco.config.js:10:28)
error Command failed with exit code 1.
```

## Root cause (app source — NOT a deployment manifest issue)
`frontend/craco.config.js` runs a prebuild hook on every **production** build:
```js
// craco.config.js line 10 (runs when NODE_ENV === "production")
require('child_process').execFileSync('python3',
  [path.resolve(__dirname, '../scripts/package_local_engine.py')], { stdio: 'inherit' });
```
Called with **no arguments**, `package_local_engine.py` runs in *verify-only* mode (`verify_runtime()`) — it checks that the browser game runtime assets already exist under `frontend/public/local-runtime/` and does NOT download them.

The deployed source only contains part of that asset set. Present: `pyodide.js`, `pyodide.asm.js`, `pyodide.asm.wasm`, `pyodide-lock.json`, `manifest.json`. **Missing**: `python_stdlib.zip`, `game.zip`, and all the `.whl` wheels (pydantic, cffi, micropip, pymunk, pathfinding, etc.).

Why they are missing from the deploy source:
- The asset set is produced by `python scripts/package_local_engine.py --runtime` (downloads from jsdelivr CDN / GitHub / PyPI and builds `game.zip`). That generated set never made it into the committed/deployed source.
- The repo root `.gitignore` (line 68-71) ignores archive assets:
  ```
  **/*.zip
  **/*.tar.gz
  ...
  ```
  This specifically prevents `python_stdlib.zip` and `game.zip` from ever being committed, so the verify step can never find them in a clean checkout.

## Verification (reproduced in sandbox on this run's source)
- `python_stdlib.zip` from the pinned CDN is reachable from the build-style network: `urllib` GET returned **200**.
- Ran `python3 scripts/package_local_engine.py --runtime` → downloaded all 15 assets and built `game.zip`: *"Browser runtime verified: 15 required assets"*.
- Then ran the EXACT build-time call (no args) from `frontend/`: *"Browser runtime verified: 15 required assets"* → passes. This is the call `craco.config.js` makes, so the frontend build would proceed past this point.

## Suggested fix (Code — E1)
Pick one (option A is the smallest, verified change):

**Option A — make the prebuild download the runtime during the build.** In `frontend/craco.config.js` line 10, pass the `--runtime` flag so the script downloads/builds the assets instead of only verifying them:
```js
require('child_process').execFileSync('python3',
  [path.resolve(__dirname, '../scripts/package_local_engine.py'), '--runtime'], { stdio: 'inherit' });
```
Caveat: this depends on the frontend-build container having outbound egress to `cdn.jsdelivr.net`, `github.com` (pymunk release) and `pypi.org` (pathfinding). The sandbox reached the CDN (200), but the production build network may be more restricted. If any of those hosts are blocked at build time, use Option B.

**Option B — ship the assets in the source.** Generate the full set (`python scripts/package_local_engine.py --runtime`) and commit `frontend/public/local-runtime/` including `python_stdlib.zip`, `game.zip` and the `.whl` files, and un-ignore them in `.gitignore` (the `**/*.zip` / `**/*.tar*` rules currently strip them). This removes the build-time network dependency entirely.

After the code change, re-trigger the deploy.

## Not the cause
- Not a deployment manifest fault (Dockerfile/entrypoint/nginx just run `yarn build`).
- Not secrets, DB, tier, or infra. Build never reached those steps.
